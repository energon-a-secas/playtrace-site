Playtrace / Implementation plan / 11 October 2026

From source posts to richer,
traceable game profiles.

Improve the evidence we retain, connect each game to its builds and destinations, then enrich the catalogue through the APIs and integrations already available.

Planning deliverable following the community insights investigation. “Post” here means the source Reddit post and its presentation inside Playtrace. Reddit posts themselves are not edited or republished. Production records and integrations were not changed during this investigation.

01 / Recommended scope

Enrich the existing catalogue before adding more providers.

The current snapshot contains 1,296 entries, 1,384 source posts and 526 project links. Its largest gaps are already addressable with better use of Reddit source text, Steam, itch.io and the linked project websites: 771 nonspecific genres, 737 unspecified stages, 883 missing device lists and 1,162 headline-based summaries.

The first milestone is a complete, reviewable profile for a 100-entry pilot. Preserve the actual game name, a useful description, source attribution, all relevant destinations, build type, supported systems, available media and the evidence behind each field. Then apply the same pipeline to the full catalogue in bounded batches.

Use existing Cloudflare D1/R2, the editorial queue and Jev. Steam public requests and limited public GitHub requests can be piloted without new credentials. The itch token is already integrated, but it does not grant access to every creator’s private game statistics.

Three code-level gaps drive the plan: source bodies are used during classification but most stored summaries become the Reddit headline; ingestion skips already-processed source IDs; and link selection reduces several useful URLs to one project URL plus a repository. Add source refresh and multiple destinations before expanding automatic interpretation.

03 / Enrichment design

Separate observations, suggestions and accepted facts.

Read source → extract evidence → resolve project/build identity → fetch linked sources → compare facts → review exceptions → publish accepted metadata → refresh dated insights

1. Retain useful source evidence and detect changes

Add an allowlisted, bounded source record with source ID/URL, content hash, source-created/edited timestamps where present, archive-observed/retrieved timestamps and extraction version. Keep excerpts sufficient to explain a fact; do not mirror entire posts publicly. A changed body or newer parser creates a new extraction job. A transient fetch failure preserves the previous evidence with its original date.

Separate “latest observed post” from “coverage complete through.” Continue the exact Demo | Project | Workflow inclusion rule, with individual review for older unlabeled showcases. Source refresh must also inspect removal/flair changes and respect existing removal tombstones. Linked Discussion/News posts may supply explicitly labeled context but never automatically become catalogue entries.

2. Preserve all destination roles

Add multiple project destinations with roles such as play, store, wishlist, download, repository, devlog and trailer. Use provider IDs and normalized URLs to create candidates; preserve significant URL paths and query parameters. The existing projectUrl remains the preferred CTA for compatibility.

Follow a bounded reference graph: at most one additional hop and ten relevant destination candidates in the first implementation. A link to an engine, hosting service or another person’s game is context, not automatically this project. Shared maker identity, canonical URL and store app IDs support matching; similar titles alone require review.

3. Model builds and lifecycle independently

A canonical game may have a browser prototype, a downloadable demo, a Steam playtest and a paid release. Each build keeps purpose, access policy, destinations, supported systems, version/date and evidence. Store application release dates belong to that application/build. Add Early Access/full-release status only when supported; never derive it solely from “coming_soon: false.”

4. Accept facts according to field-specific rules

Names: explicit admin override, then verified store/creator naming, then explicit source naming, then URL/README candidate, otherwise leave a review task. Preserve the Reddit headline as supporting source context. Images: keep approved uploads first, then approved store/source artwork, then a useful video poster candidate. Lifecycle, access and genres: retain conflicting statements and review context instead of applying one global “newest source wins” rule.

Every fact needs its value, source locator or text span, observed date, applicable project/build, extraction version and review state. Jev suggestions carry the returned model version and score, including an unknown/insufficient evidence option. Probability alone does not authorize publishing or merging.

5. Treat creator context and player feedback separately

Creator replies can clarify the name, engine, build URL, intended controls or planned feature; route them to metadata evidence. Player comments become a separate feedback sample, with parent context when necessary, actual comment links and inclusion/exclusion counts. Preserve complaints, praise, uncertainty and contradictions. Keep Reddit, Steam and Playtrace contributions as distinct populations.

Reuse the already collected two-month archive window when suitable. For ongoing work, target known source posts, checkpoint cursors, and periodically sweep older projects so “recent comments on an old game” is not missed. Choose targeted requests or bounded archive batches according to measured coverage/cost; do not classify the whole subreddit repeatedly.

04 / What changes in each entry

Give visitors a useful game profile and a readable source history.

  • Game identity: actual title, short evidence-backed game-loop description, maker attribution and original Reddit headline.
  • Try it: clear actions for browser build, demo/download, store/wishlist and source code; show access requirements and last check.
  • Understand it: primary/secondary genre, mechanics, themes, player modes, supported devices/OS, build purpose and lifecycle as separate fields.
  • See it: approved main image with source attribution; screenshots and trailers as secondary assets. Retain upload overrides and avoid a black opening frame as the only preview.
  • Follow progress: source timeline, explicit release/build events, what changed in an update, and related devlogs/reference links. Do not reinterpret every promotional repost as development progress.
  • Learn from feedback: dated, editor-approved themes with numbered original-comment links, sample counts, disagreements and exposure context.

07 / Quality gates

Prove improvements before accepting a catalogue-wide change.

  1. Identity: no merging a demo app into a different game; no source/tool links mistaken for the project; proposed duplicate merges preserve aliases, contributions and history.
  2. Evidence: every accepted enriched field has an inspectable source and observation date. Unknown, conflicting and stale remain distinct.
  3. API contracts: fixture coverage for missing fields, changed shapes, zero reviews, region/currency differences, redirects, 304/403/404/429/timeouts and provider pagination.
  4. Editorial precedence: repeated refresh cannot replace the approved Manor thumbnail or an admin-corrected title. An admin can explicitly accept a new suggestion.
  5. Publication: preserve the catalogue’s flair rule and removal controls. A referenced discussion is context, not a newly eligible game. No withdrawn source text or private research appears in public exports.
  6. Metrics: project counts, build counts and source-post counts reconcile separately. No duplicate price votes or review evidence after retry; no completion-rate claim based on retained-only quiz starts.
  7. Operational: campaign progress survives interruption; one provider outage does not block others; public reports use cached aggregates; fallback dates remain truthful.

Track field coverage before and after the pilot, broken-link repair rate, accepted/rejected suggestion counts by provider, unresolved identity conflicts, human classification agreement and processing cost per entry. Set expansion targets from that evidence. Do not convert missing values into guesses just to make the completeness percentage increase.

08 / What the community gains

Insights that follow directly from stronger evidence.

  • Discoverability: games by genre/mechanic, available browser builds, downloadable demos and supported systems, with unknown coverage shown.
  • Release activity: actual demo, playtest, Early Access and full-release events separated from first Reddit appearance and promotional updates.
  • Development learning: creator-reported engine and AI-workflow usage; source-linked progress; time from first observed showcase to a later evidenced build milestone, with incomplete follow-up acknowledged.
  • Player feedback: reviewed themes and unresolved issues by build and source; comparison of Reddit impressions, store reviews and Playtrace responses without pooling them into one score.
  • Price context: fresh regional store prices and optional ideal-price responses shown separately. Neither is a sales/revenue estimate.
  • Catalogue health: missing names/genres/links, stale evidence, broken destinations, preview failures and unreviewed changes.

Player expectations still require asking players. APIs can describe games and retrieve observed opinions; they cannot establish what Playtrace visitors expected, intended to pay or planned to play. Add the short contextual questionnaires from the earlier report alongside the enrichment rollout, keeping sample size and exposure context visible.

The initial public release should combine improved project pages with a modest “Community insights” view. Defer popularity rankings, developer success scores and market-demand predictions: the available sources do not support them.

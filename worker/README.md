# Playtrace Worker

Native ES modules serve the v1 API with D1, public guest feedback, optional private R2 previews, Clerk sessions for legacy account features, and bounded historical/recent archive ingestion. No frontend build or server package dependency is required. [The guest/history API contract](../docs/public-feedback-api.md) extends the original workspace contract at `docs/delivery/playtrace/CONTRACTS.md`.

Run from the project root with Node 22.13+ (the tests use built-in SQLite):

```sh
node --test worker/tests/*.test.mjs
python3 worker/tests/schema.test.py
```

The request tests use actual RSA signatures and SQLite transactions. Test-only fixtures inject network responses and time through `createWorker()`. The production entrypoint has no environment authentication bypass. These tests do not prove real Clerk sign-in, real user willingness to pay, or live Cron execution.

## Provisioning and enablement

1. Provision D1 and apply the migrations in order: `0001_initial.sql`, `0002_public_feedback.sql`, `0003_history_pagination.sql`, `0004_editorial_tools.sql`, `0005_quick_feedback.sql`, `0006_name_game.sql`, `0007_project_details.sql`, `0008_game_categories.sql`, `0009_discovery_research.sql`; bind it as `DB`. Apply only migrations not already installed. Migration 0004 adds editorial tools, 0005 preserves feedback while permitting choice-only contributions, 0006 adds quiz rounds and guesses, and 0007 adds project detail overrides, and 0008 adds the shared category registry (including Clicker). Migration 0009 adds ratings, aliases, source references, store enrichment, questionnaires, responses and editorial jobs. None copy private prices. Deploy the Worker after its migrations and before the new frontend. `wrangler.jsonc` contains the operator-provisioned database identifier. Rollback SQL is for disposable test databases only.
2. Set `ALLOWED_ORIGINS` to exact site origins and `CLERK_ISSUER` to the fixed Clerk issuer origin. Session JWTs use the default session token, RS256, and its pinned `/.well-known/jwks.json`; no custom audience or Convex template is required.
3. Set `RATE_LIMIT_SECRET` and `OPERATOR_TOKEN` as independent Worker secrets, each generated from at least 32 random bytes. Use 64 hex characters or base64url encoding. Do not put either secret in the site, URLs, committed files, command history, or logs. `.dev.vars*` and `.env*` files are ignored.
4. Choose `SIGNAL_PROTECTION` on the server. The provisioned baseline is `account-rate-limit`, requiring signed accounts, one current signal per account/game, and account plus daily-HMAC-network rate limits. The default when absent is `turnstile`, which requires `TURNSTILE_SECRET_KEY`, `TURNSTILE_HOSTNAME`, and a corresponding browser site key. Unknown values disable signals. The browser reads the mode from `/status`; client input cannot select it. Never deploy a Turnstile testing secret.
5. Seed using operator-authenticated `POST /api/v1/admin/catalog` with the complete validated `data/catalog.json`. Keep the bearer credential private. Import is one six-statement D1 transaction, preserves existing published timeline entries, and cannot overwrite tombstones or invent R2 consent.
6. Check `/status`, all `/catalog` pages, and anonymous feedback reads. Guest feedback requires `DB` and `RATE_LIMIT_SECRET`, independently of Clerk and `SIGNAL_PROTECTION`. Verify positive guest writes in a local or staging database; production probes must not invent public activity. Empty/unconfigured services return 503. Verify account flows separately after the fleet Clerk instance permits the live domain.
7. Set `INGESTION_ENABLED=true` for manual operator ingestion. Invoke `POST /api/v1/admin/ingest` repeatedly until the frozen initial seven-day window completes. Each call processes at most three 100-row pages, waits 600ms between successful pages, and performs at most two bounded retries per failed request. Requests use `limit=auto` to avoid fixed-limit timeouts on sparse windows; recent pages retain the newest 100 rows and advance only to that retained boundary. Partial runs save `resumeBefore`, `resumeAfter`, and `targetCoverageThrough`; they do not claim new complete coverage. Normal runs overlap the last completed coverage by 48 hours.
8. Archive collection uses `35 * * * *` (minute 35 of every hour, UTC). The recent pass runs first. Only a completed recent pass starts the independent historical pass; a partial/throttled recent run defers it. Historical collection starts at the community's creation, `2022-12-11T12:00:48.000Z`, and advances in ascending date order, one adaptive page of up to 1,000 rows per invocation. `POST /api/v1/admin/backfill` with `{}` lets an operator resume the same history checkpoint without rerunning the recent window. It is a no-op after completion. Respect upstream rate limits rather than repeatedly triggering either endpoint.
9. `/status.history` reports `startedAt` and the current `scannedThrough` checkpoint; `completedThrough` is populated only after the frozen historical window completes. `/status.ingestion.coverageThrough` remains the independent recent coverage marker. Archive collection and guest/account writes delete expired rate rows; keep hourly collection enabled while accepting contributions.

A separate `5 * * * *` trigger runs store/media maintenance at minute 05. It refreshes at most six due Steam apps, then hydrates ten source posts only when both recent and historical checkpoints are complete. Keeping this separate from archive collection prevents their combined D1 work exceeding the per-invocation budget. Full-handler regressions cover cold Steam caches plus hydration and enforce fewer than 50 D1 statements, including the operator enrichment route.

The full 300-candidate ingestion test stays within the per-invocation D1 budget, with JSON-bound bulk writes. A scheduled invocation can run both a recent and historical pass. Public catalogue pages contain at most 200 games, sorted by `updated_at DESC,id ASC`, and include `pagination.total` and `pagination.nextCursor`. Follow the cursor until null; there is no 2,000-game total cap. Operator import envelopes retain a 2,000-record batch bound and cannot include the API-only pagination field.

Source IDs remain idempotent. Historical requests process one adaptive page of up to 1,000 rows per invocation; recent passes process at most three 100-row pages. Only the exact `Demo | Project | Workflow` Reddit flair is eligible for automatic publication. Unlabeled candidates stay pending, including those matching an existing project. A reviewed operator import may include an older unlabeled game showcase with `flair:null` and `inclusion:"reviewed-unlabeled-game"`; explicitly excluded flairs cannot use this exception. The reviewed builder requires an individual review reason and source-supported project links. The importer publishes clear game showcases with `reviewStatus:source-described`, conservative source-evidenced taxonomy and stage, and original titles. Same author plus canonical project URL can attach an older source while keeping the game's original ID and all associated data. The original source anchor must remain in the timeline; `firstSeenAt` and `updatedAt` always reflect the minimum/maximum source dates. Ambiguous candidates and timelines exceeding 1,000 sources remain pending. Review and publication use normalized operator imports, not raw archive copying. A full nonadvancing timestamp page records `CURSOR_STALLED` and requires operator investigation; it never claims complete coverage.

To review an existing catalogue, retrieve every current source ID from the archive, then run `node scripts/review-source-flairs.mjs --catalog /path/to/catalog.json --raw /path/to/posts.json --output /tmp/flair-review`. Inspect the generated catalogue, review evidence and SQL before applying the SQL. The script refuses incomplete source evidence or source-anchor/preview-attribution conflicts. Excluded projects are hidden, their source rows rejected, and contributions retained. `data/source-flair-review.json` records the completed 361-post review: 152 of 350 projects remained eligible.

## Guest feedback and moderation

Public reads and writes never require Clerk. A browser creates a 256-bit edit key and passes it only in `X-Feedback-Key`; the Worker stores an HMAC, not the raw key. One contribution per game and key can contain quick multi-select choices, an optional note, display name, and USD ideal price. Choice-only submissions are valid; public aggregates count all published contributions. New public medians include all published guest prices, including small cohorts, because each individual suggestion is already expressly public. Legacy `price_signals` keep their separate privacy threshold and are never included.

Writes allow ten saves per edit key per hour and sixty per network per hour, plus the shared subject quota. Network bucket keys use a daily HMAC; raw addresses are not persisted. Deletion has a separate quota so reaching the save cap does not prevent removal. Rotating `RATE_LIMIT_SECRET` also invalidates existing guest edit keys because their identity HMAC changes; treat it as a data-access migration and retain operator removal assistance. Neither a key nor a network identifies a unique human.

Every contribution has a correction/report link. An authenticated operator can hide one using `POST /api/v1/admin/feedback/:id/hide` with `{"reason":"…"}`. Hidden text and prices disappear from public reads and medians. The retained hidden row blocks the same key from immediately reposting to that game; it is not a global identity ban. A different browser key can still be created, so moderation and edge abuse controls remain necessary.

## Screenshot recognition game

The [quiz API contract](../docs/name-game-api.md) covers five randomized screenshots from 20 curated playable projects. `src/quiz-pool.mjs` defines verified names and original-host images; `data/quiz-review.json` records provenance. `/quiz` reports availability. Guest start, completion and removal use a separate HMAC identity domain from feedback. The server chooses questions and computes scores; retried completion does not duplicate answers. Skips are not wrong guesses. `/admin/quiz-metrics` requires a verified editorial admin and returns per-game chosen-name distributions. Clerk setup affects that private dashboard, not guest play. Test real writes only in disposable storage.

The simplest local check is `node --test tests/*.test.mjs worker/tests/*.test.mjs`: it exercises guest flows against disposable in-memory SQLite with no production writes. To browse the static snapshot, run `make serve` and temporarily set `apiBase: ''` in `js/config.js`.

For an interactive Worker preview, use installed Wrangler with `--local` and a disposable local D1 database. Apply all migrations locally, seed through the local `/admin/catalog`, and provide test-only `RATE_LIMIT_SECRET` and `OPERATOR_TOKEN` in ignored `worker/.dev.vars`. Set local `ALLOWED_ORIGINS=http://localhost:8900` and `INGESTION_ENABLED=false`. Run `wrangler dev --local --config worker/wrangler.jsonc --port 8787`; temporarily pin `apiBase` to `http://localhost:8787/api/v1` and add that exact origin to the local HTML's `connect-src`. Keep `accountsReady:false`. Restore those local edits before publishing; production CORS and CSP must remain pinned. Never pass `--remote` or seed test comments into the production database.

## Compatible rollback

Export production data before any schema rollback. Prefer a forward fix or a compatible Worker that disables guest writes and historical collection while preserving the new source-anchor validator and catalogue pagination. Once earlier sources have attached, the original earliest-post-only validator cannot serve those timelines. Once the archive exceeds 2,000 projects, the original unpaginated catalogue cannot serve it either. Do not restore that old Worker wholesale or run the destructive rollback SQL in production. Keep the feedback table for privacy/removal requests; a feature rollback must not silently discard public contributions.

## Consent previews and removal

Bind the private bucket as `PREVIEWS` and set exact `PREVIEW_ALLOWED_HOSTS`. The operator-only preview endpoint requires a creator-consent evidence URL and note. It accepts HTTPS PNG/JPEG/WebP up to 5 MiB, with matching MIME/signature, streaming limits, no redirects, and no IP-literal/private-host selection. Consent is audit data and never appears in the catalogue. Videos and GIFs can be linked as secondary assets, with explicit playback and an original-post fallback.

Uploaded previews use `/api/v1/media/:assetId`, authorized by R2 publication and withdrawal records on every read, without a D1 query, with explicit MIME, `nosniff`, and `no-store`. Public bucket URLs are not used, so the Worker can suppress access immediately after removal.

Removal first commits the tombstone, hides/scrubs the game, and deletes source identities, public feedback, quiz answers involving the game, change requests, image overrides, follows and private prices. A per-game media lease prevents cleanup from racing an upload. Storage failure or an active upload returns 503 while the game stays unavailable; retry the same removal until it succeeds. Object keys survive failed cleanup. Tombstones survive game deletion and prevent reimport under a different game ID.

After a removal, regenerate `data/catalog.json` from all live catalogue pages (omit API-only `pagination` and each game’s `steam` metadata from an operator import envelope) and publish it. The static snapshot is a separately distributed file and cannot be erased by a Worker database transaction. External source media may disappear independently. Catalogue responses may be cached for sixty seconds; feedback/media reads use `no-store` and deny removed projects immediately. Configure deployment edge limits for public endpoints.

## Source enrichment and read budgets

Apply migration `0010_source_evidence.sql` before deploying this release. It adds retained source evidence, queue indexes and a transactional catalogue count. Export a backup first. The migration also makes legacy basic-only Steam records due for the existing six-app refresh batch. Keep all admin overrides and R2 publication records intact.

Anonymous discovery cache keys now use a strongly consistent R2 revision record at `discovery/revision.json`; warm hits require no D1 queries. Authenticated/private requests bypass this cache. A failed R2 read uses a fresh database response rather than an unchecked cached response. Mutations invalidate the revision, including failed removal cleanup after a committed tombstone. An already exhausted D1 allowance still prevents uncached database reads until the quota resets; the dated static catalogue remains the discovery fallback. No billing plan change is required by this release.

Catalogue pagination reads the `catalog_total` counter instead of recounting every project. Database triggers maintain it across imports, status changes, removals and deletion. Never edit that value manually; compare against the eligible-game count during database audits. The page cursor also constrains the date index before applying its tied-date condition.

At minute 45, a separate hourly task refreshes at most ten known Reddit posts, starting with missing evidence and then records older than seven days. Recent ingestion refreshes known posts in its overlap window, and the existing References queue action also refreshes their prose. Source identity, membership, manually edited fields, approved images and history dates remain authoritative. Full source bodies are bounded to 40,000 characters in the internal `source_evidence` table, with content hashes, source edit/archive timestamps and separate checked/changed dates. Public excerpts remain plain text, at most 600 characters. Removed prose is cleared, missing archive rows are not treated as deletions, and source removal cascades the evidence. A concurrent game update aborts the source batch for retry.

Explicit current-source reviews in `data/current-showcase-review.json` can supersede only the exact older archive observation that was reviewed. The Manor is one such case. Newer archive observations, changed authors and explicit deleted text cannot use this exception; excluded flairs never become new catalogue entries through refresh.

Editorial work reserves its attempt budget before contacting a provider. `EDITORIAL_DAILY_LIMIT` defaults to 72, resets at 00:00 UTC and accepts 1–200. Failed attempts count. This caps queued operator/admin/cron work; hourly ingestion, six-app Steam maintenance and ten-post source maintenance remain separately bounded. Increasing the cap is an operational decision, not a way to bypass D1 limits. No-op maintenance runs leave discovery caches intact.

The hourly editorial tick processes at most two jobs (48 scheduled attempts per day), leaving headroom within the default daily cap for manual work. The admin Run next action still processes one job. Store descriptions can replace a placeholder or an unchanged automatic source excerpt; custom/editor-reviewed descriptions stay in place, and the source excerpt remains in the history.

The `5,45 * * * *` schedule uses the event's scheduled minute to separate Steam/media maintenance from source refresh into different invocations. It occupies one cron definition, keeping the deployment within five cron triggers. Allow Cloudflare's trigger propagation time after changing the schedule.

Steam records retain the store description, supported operating systems, genres/features, developer/publisher labels, displayed release date, up to six approved-CDN screenshots, and a demo's parent game. `releaseKind` distinguishes a demo, Early Access and a game listing; the separate release state still distinguishes upcoming listings. Missing platforms and placeholder descriptions can use store evidence; admin values and uploaded thumbnails always win. Parent links and attributed screenshots appear in project notes. Existing price freshness and USD-only validation remain in force. The public appdetails endpoint is best effort; malformed/failed refreshes retain the last successful result with its original date.

The itch.io adapter now retains versioned public listing facts: structured title/description, explicit platforms, creator-listed status, genres, tools, inputs, languages, AI disclosure and up to six allowlisted screenshots. `provenance` identifies the source field for each observation; `sourceUrl` and `storeCheckedAt` locate and date the evidence. Browser players and download controls support build availability; a purchase/preorder control or a published listing alone does not. Creator-listed status does not automatically change the catalogue to a full release. Admin edits and approved images remain authoritative. Optional owner-authorized itch API metadata never stores earnings or purchases, and an API failure does not discard a successful public-page check. Non-HTML/challenge pages retain prior store facts with their original check date.

Favorites first persist on the visitor's device. Signing in moves anonymous saves into an account-specific local outbox and unions them with server favorites. `PUT /api/v1/me/favorites` accepts at most 200 explicit `{gameId,saved}` changes per authenticated, rate-limited transaction, resolves aliases and ignores withdrawn entries. Acknowledgements are matched to local operation revisions so late responses cannot undo newer edits. Signing out hides account caches; deleting account data clears its local outbox after pending writes finish. No login or API connection is needed to use local favorites.

Verified admins can remove an entry through `POST /api/v1/admin/games/:id/delete` with `{confirm:gameId,reason}`. This uses the existing tombstone/media withdrawal process and records the admin actor. The inline editor presents the exact target and the loss of contributions before submission. `POST /api/v1/admin/games/:id/posts/:postId/remove` instead excludes an extra history post, preserving the entry and contributions; the only source and preview-credit sources are protected. Excluded source IDs remain rejected during ingestion and cannot be resurrected by a stale import. Snapshot guards reject concurrent project/image edits. Nearby same-author posts and matching links/titles are review flags; automatic repost consolidation retains its stricter existing rules.


### Discovery pages, insights and anonymous counts

- `GET /games/:id` returns the current public catalogue record and follows a merge alias. Withdrawn records return 404. It uses the same versioned public cache as the catalogue.
- `GET /admin/insights?cursor=...` returns at most 200 projects per page with public-safe mention evidence. Verified Clerk admin authorization is required; responses are `no-store`. No private feedback, user IDs or jobs are read by this projection.
- `GET /insights?cursor=...` exposes the same allowlisted source projection publicly, including reviewed field provenance and exact linked Steam release dates where available. Its versioned cache expires after 60 seconds. Pages publishes a complete dated snapshot hourly; the dashboard falls back to this endpoint when that snapshot is missing or stale. Account records, visitor activity and private questionnaire answers are excluded.
- `POST /usage` accepts up to ten allowlisted anonymous actions, random delivery IDs and a published game ID where needed. Retry receipts expire after 24 hours; rate buckets use an hourly rotating HMAC of the network address. DNT/GPC and obvious bots are ignored. No fingerprint, persistent visitor ID or event stream is retained.
- `GET /admin/usage` returns daily action totals and aggregate contribution counts. It requires verified admin authorization and does not expose private questionnaire text or account identities.

Apply `0011_usage_metrics.sql` before this Worker release. The :50 maintenance invocation prunes expired anonymous totals/receipts alongside duplicate maintenance. Rollback `0011` only after deploying a Worker that no longer reads those tables. No schema rollback is needed for a code rollback to the prior release.

Apply `0012_reviewed_project_facts.sql` before publishing the evidence pilot Worker. Accepted field observations retain their source, quote and check time separately from source imports. Administrator edits take precedence. Source removal clears facts citing that post; merges preserve the receiving project's accepted facts. Rollback `0012` only after deploying a Worker that no longer reads `project_facts`. The [100-project pilot](../docs/enrichment-pilot100.md) describes preparation, conflict guards and preservation checks.

Built-in review studies are seeded with conflict-safe inserts. Difficulty, Controls, Accessibility and Link Health are included; administrator edits and inactive states survive reseeding. Public topic options reflect active forms only.
